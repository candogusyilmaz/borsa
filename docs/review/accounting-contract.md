# Accounting contract

Contract date: 2026-08-07

Status: initial implementation contract for the scratch rewrite. This file governs cross-cutting financial semantics shared by ledger, investing, observations, valuation, performance and scenarios. Feature-specific rules belong in their feature design documents; they must not contradict this contract.

## 1. Authority and change rule

- [backend-master-plan.md](backend-master-plan.md) controls implementation order and architectural scope.
- This document controls shared financial semantics.
- A slice may add a feature-specific invariant without editing this file when the invariant does not change another capability's interpretation of money, time, quantity, valuation or return.
- A change to posting signs, economic ordering, fee/tax treatment, cost basis, FX selection, balance definitions, valuation, performance methodology or projection state requires this document and the affected hand-worked golden fixtures to change before production code.
- Posted facts created under an older schema/methodology remain auditable through their stored schema/calculation/policy versions; do not silently reinterpret a previously exported calculation run.

## 2. Numeric representation and rounding

- Java authoritative calculations use `BigDecimal`.
- PostgreSQL authoritative money/quantity/rate inputs default to `numeric(38,18)` unless a stricter domain range is justified.
- Public API money, prices, quantities, rates and percentages are canonical decimal strings, never binary floating-point numbers.
- Numeric zero/equality checks use numeric comparison (`compareTo`) rather than scale-sensitive `BigDecimal.equals`.
- Storage/calculation precision is separate from display rounding.
- Intermediate financial calculations do not round merely for presentation. Round only at a real domain boundary such as a currency minor-unit settlement, provider-defined precision, tax/policy rule or explicitly versioned calculation rule.
- When a minor-unit remainder must be allocated, use a deterministic documented allocation rule and test the remainder explicitly.

## 3. IDs, clocks and reproducibility

- User-owned aggregates, immutable activities, imports, scenarios and calculation runs use UUID identifiers generated by the application.
- Reference rows use stable codes only when the code is genuinely the identity (`TRY`, `USD`, ISO country code); otherwise use UUID.
- Production code obtains current time through an injected `Clock`; tests/demo scenarios use a fixed clock.
- Demo/test IDs may be deterministic, but normal user IDs must not encode user data.
- Reproducible calculation/scenario output pins the fact watermark, observation revisions, policy versions, source-selection policy and calculation version used by the run.

## 4. Time model and economic ordering

Each immutable activity stores at least:

- `effectiveAt` — when the economic event takes effect;
- `recordedAt` — when the application accepted the fact;
- `settlementAt` when settlement differs from execution/economic time;
- source/client/external identity and provenance;
- an economic sequence/order value when multiple events at the same effective instant can produce different valid outcomes.

Ordering rules:

1. Replay uses economic time, never database insertion identity.
2. Primary order is `effectiveAt`.
3. When same-instant order can affect quantity, balance, basis or validity, a deterministic `economicSequence` must be supplied or derived from trustworthy source order.
4. If same-instant order is economically material and cannot be resolved, commit/import must require review instead of inventing order from database ID, random UUID or request arrival order.
5. Stable IDs may break ties only when the remaining events are commutative for the affected invariant.
6. `recordedAt` is audit/provenance information and is not a substitute for economic ordering.

Backdated insertion, correction or revised observations invalidate projections from the earliest affected economic date/time.

## 5. Actual, obligation, plan and scenario boundaries

- **Actual**: committed ledger facts and accepted/reconciled observations. Only actual facts alter actual balances/positions.
- **Obligation**: issued/owed commitments such as bills/debt requirements. They may affect committed/available/forecast views but not historical cash until posted. An intended funding account or payment rule is planning metadata only; it does not authorize/initiate money movement. The actual payment is a later posted fact linked back to the obligation.
- **Plan**: goals, expected bills, reservations and intended future transfers. Plans never create actual money movement.
- **Scenario**: hypothetical/counterfactual calculations. Scenario output never posts ledger facts.
- Unreviewed document/AI extraction is preview evidence only and cannot create actual facts before explicit validation/commit.

## 6. Opening state and historical coverage

A user may start tracking without reconstructing prior financial history. An opening state is an explicit assertion of what is known at the beginning of tracked coverage, not a normal income/spending/performance event.

Supported opening-state examples include, as the relevant feature slices become available:

- cash/current/savings account balance;
- physical cash balance;
- credit-card or loan liability balance;
- brokerage cash;
- existing security quantity and known cost-basis information;
- receivable owed to the user;
- payable owed by the user.

Rules:

1. Every opening assertion has an effective time/date and source/provenance, normally `USER_ENTERED`.
2. Store/derive a historical-coverage boundary for the affected account/holding/claim. History before that boundary is unknown unless later imported/reconstructed and reconciled.
3. An opening cash balance is not income or contribution merely because it increases tracked state.
4. An opening liability is not spending. An opening receivable is not income. An opening payable is not spending.
5. Opening security state must state whether quantity, economic basis and cash history are complete. Unknown basis remains unknown; do not invent acquisition cash or performance.
6. Analytics whose requested period crosses an incomplete coverage boundary expose incomplete coverage and must not imply fully reconstructed performance/cash-flow history.
7. Later historical imports may reconcile/supersede an opening assertion when the application can prove the reconstructed history explains the same boundary state; do not silently double-count both.

## 7. Immutable activities and corrections

- Posted financial facts are immutable.
- Do not update/delete a posted fact to make history look as if the original never existed.
- Correction uses an explicit supersession/replacement relationship or a reversal plus corrected fact, depending on activity semantics.
- Reversal must negate the economic effect while retaining the original and correction relationship for audit/export.
- There is no destructive `undo latest` financial command.
- Replay after correction must produce the same projection as if the corrected economic history had originally been entered in that economic order, while preserving the audit trail.

## 8. Signed posting convention

`money_posting.amount` uses the account owner's balance-sheet direction:

- positive amount increases the account's represented balance/value;
- negative amount decreases it.

Examples:

- cash deposit into an asset account: positive cash posting;
- cash withdrawal/payment from an asset account: negative cash posting;
- credit-card purchase: liability balance increases according to the liability account's normalized outstanding-balance model; reports must not treat the later card payment as new spending;
- transfer: source and destination legs move value without creating income/spending/performance except explicit fee/FX components;
- receivable/payable settlement: cash moves and the claim balance decreases; repayment of money owed is not income to the creditor and is not new spending by the debtor;
- borrowing principal: increases cash asset and liability outstanding, not income;
- principal repayment: decreases cash and liability outstanding, not spending except separately identified interest/fees;
- security quantity uses its own signed quantity convention: buy/acquisition positive, sell/disposal negative.

Account-kind normalization must make asset, liability, available-credit and net-worth reporting explicit. Do not infer income/expense solely from the sign of a posting; posting role/activity type carries economic meaning.

## 9. Trade, settlement, fees and taxes

A funded trade records linked cash/security economics rather than mutating a position as the source of truth.

### Buy

- Security quantity becomes effective at execution/economic time.
- Cash/proceeds postings identify settlement state and optional `settlementAt`.
- Buy transaction fees are stored exactly in their native currency.
- For the initial **economic performance** cost-basis policy, directly attributable buy transaction fees are capitalized into economic cost basis.
- Taxes/levies are stored as distinct components. Their inclusion in economic P&L is explicit; jurisdictional tax-basis treatment belongs to a separate versioned tax policy.

### Sell

- Disposed security quantity becomes effective at execution/economic time.
- Gross proceeds, sell fees and tax/withholding are retained as separate facts/components.
- Sell fees reduce net proceeds for economic realized P&L.
- Tax/withholding is reported separately and included in net-after-tax views only when that view explicitly requests it.

### Settlement

- Execution/effective time and settlement time are distinct where the source supports that distinction.
- `cleared`, `pending`, `available`, `reserved` and `committed` are separate views; a pending settlement must not be silently described as cleared cash.
- If a broker executes FX, preserve both currency legs, execution rate, spread/fee and source evidence.

## 10. Cost-basis policy

The initial performance policy is versioned weighted-average economic cost basis (`WEIGHTED_AVERAGE_ECONOMIC_V1`). It is not a jurisdictional tax calculation.

Rules:

- quantity and remaining basis are derived by replay from immutable activities;
- buy basis includes directly attributable buy transaction fees under the initial policy;
- partial disposal removes the proportional weighted-average basis of disposed quantity;
- sell fees reduce net proceeds rather than remaining basis;
- full close must leave quantity and remaining basis numerically zero;
- reopening after a full close starts a new economic holding cycle while prior facts remain in history;
- fractional quantities are first-class;
- invalid historical short/negative quantity is rejected unless the account/instrument explicitly supports that behavior.

Future FIFO/specific-lot/jurisdictional pooling policies must be separate named/versioned policies. Tax reporting must record which tax policy/version produced its result and must not overwrite the economic-performance basis.

## 11. Currency and FX contract

- Every authoritative fact retains its native currency and amount.
- Executed FX is a transaction fact; reference/market FX is observation data. Do not replace one with the other.
- Conversion occurs only in valuation/reporting/scenario calculation under an explicit source-selection policy.
- For an as-of calculation, select only observations whose effective/publication rules make them knowable at that as-of time. No look-ahead.
- Default historical valuation rule: use the highest-priority acceptable observation at or before the requested as-of time and within the configured staleness/calendar policy.
- Never use today's mutable FX rate to translate historical facts.
- Never silently fill a missing historical FX rate with a future observation.
- Manual override/fallback is permitted only when the selected policy explicitly allows it and the derived result exposes that manual source/fallback.
- If no acceptable FX observation exists, the converted value is unknown/unpriced and coverage metadata states the gap; do not substitute a plausible current rate.

## 12. Observation/source selection

An observation source-selection policy defines:

- accepted source kinds (`USER_ENTERED`, `FILE_IMPORTED`, `SYNTHETIC`, `PROVIDER`, as applicable);
- source priority;
- requested/as-of time and publication/no-look-ahead rule;
- maximum staleness/calendar carry rule;
- missing-data behavior;
- manual override/fallback permission;
- interpolation policy when explicitly supported;
- acceptable quality/revision state.

Calculation services consume normalized stored observations selected through this policy. They never call provider HTTP APIs directly and never invent their own fallback hierarchy.

## 13. Balance definitions

Do not expose one overloaded `balance` field when the account can distinguish the following:

- **ledger balance** — sum of posted ledger facts under the account's accounting convention;
- **cleared balance** — settled/cleared amount;
- **pending** — accepted but unsettled/pending effects;
- **reserved/committed** — value reserved for known commitments where modeled;
- **available** — amount usable under account restrictions/negative/credit policy;
- **authorized limit/credit** — borrowing/overdraft capacity, not an asset;
- **projected balance** — forecast result from plans/obligations, never historical actual cash;
- **reconciled statement balance** — external stated balance with reconciliation metadata; it does not silently replace ledger balance.

The API names the balance type and as-of time. Net worth uses assets minus liabilities; credit limits are not added to wealth.

## 14. Valuation contract

The valuation service is the single shared place that converts quantities/cash/liabilities into reporting-currency value.

Inputs include:

- scope (`user`, `household`, `portfolio`, `account`, selected assets);
- requested `asOf`;
- reporting currency;
- observation source-selection policy;
- inclusion rules for pending/unpriced/manual assets;
- cost-basis policy where basis is reported.

Outputs include:

- requested and actual as-of time;
- native and converted values;
- gross assets, liabilities and net worth;
- remaining cost basis and unrealized P&L under a named policy;
- priced/unpriced value/count coverage;
- oldest/stale observation information;
- selected source/revision/fallback information;
- calculation/methodology version;
- projection status where a cached projection is served.

Unknown market value remains unknown. Do not replace a missing price with average cost and present it as valuation.

## 15. Performance definitions

Do not expose a generic unlabeled `return`.

- **Absolute P&L**: currency-unit reconciliation over the requested scope/period.
- **Realized P&L**: proceeds minus allocated economic basis minus/plus explicitly included transaction components under the named policy.
- **Unrealized P&L**: current/as-of value minus remaining economic basis for valued positions.
- **Simple return**: appropriate only where intermediate external flows do not invalidate the interpretation.
- **XIRR / money-weighted return**: reflects the user's dated external cash flows.
- **TWR**: removes the effect of external contributions/withdrawals to evaluate investment performance.
- **Real return**: nominal result deflated by a named/versioned inflation/personal-basket index.
- **Benchmark-relative return**: date-aligned total-return comparison in the same reporting currency with explicit dividend/FX methodology.

Every result states period, reporting currency, flow treatment, methodology/calculation version and data coverage.

## 16. Daily change and return decomposition

Do not label raw NAV movement as investment performance.

For a selected period, the analysis engine should be able to reconcile:

`opening value + external flows + price effect + FX effect + income - fees - tax + residual = closing value`

The decomposition must keep at least:

- external contribution/withdrawal;
- asset-price effect;
- FX effect;
- dividends/interest/other investment income;
- fees;
- tax/withholding;
- residual/data effect.

A material residual is surfaced as a quality/integrity issue rather than hidden by rounding or silently attributed to market performance.

## 17. Projection consistency

All rebuildable projections use:

- `CURRENT` — every committed relevant input through the watermark is represented;
- `STALE` — a relevant input changed and rebuild is required;
- `REBUILDING` — rebuild in progress;
- `FAILED` — last rebuild failed.

Projection records/API metadata include `asOf`, input watermark/version, status, `lastSuccessfulBuildAt`, and `staleFrom` when relevant.

Rules:

- immutable source facts remain authoritative even if projections fail;
- backdated facts/reversals/observation revisions mark the earliest affected point stale;
- small rebuilds may run synchronously; larger work may use the durable job system;
- stale previous output may be shown only with an explicit stale/rebuilding/failed indication;
- deterministic replay of identical facts/observations/policies/version must produce identical projection output.

## 18. Idempotency and concurrency

- Retryable financial commands require a principal-scoped operation/idempotency key or stable client event ID.
- Repeating the same key and semantically same request returns the original result and creates one economic fact.
- Reusing a key for a materially different request is a conflict.
- Affected account/instrument projection keys are locked/versioned in deterministic order.
- Database uniqueness is the final barrier against duplicate aggregate/projection identity.
- Concurrent commands either commit a serially valid result or return a stable conflict/retry response; silent lost updates are forbidden.

## 19. Source/provenance and synthetic truth

Every imported/observed fact records enough provenance to distinguish source truth from normalized values: dataset/source, source kind, provider/external identity, effective/publication/ingestion times, revision, original unit/currency/value where retained, normalized value, quality/confidence and synthetic status.

- `REFERENCE_SEED` is stable startup/reference data only.
- `SYNTHETIC` is demo/test data only and uses isolated synthetic ownership/datasets.
- Synthetic observations or policy samples must never be presented as current official/live financial truth.
- Demo data is created through normal application command/ingestion services; derived projections are not directly seeded.

## 20. Golden fixtures

Two fixture classes are required:

1. **Small hand-worked golden fixtures** — prove mathematics and invariants with examples small enough to verify independently by hand.
2. **Deterministic household end-to-end dataset** — proves integration across real application workflows and feature boundaries.

At minimum small fixtures cover deposit/transfer neutrality, fee-aware buy/partial sell/full close/reopen, different decimal scales, backdated correction, two currencies, missing/stale observations, TWR/XIRR, FX attribution and reversal/idempotency behavior.

## 21. API contract summary

From the first `/api/v1` endpoint:

- external IDs are opaque strings/UUIDs;
- financial decimals are canonical strings;
- errors use stable RFC 9457-compatible problem codes/messages;
- potentially unbounded lists use cursor pagination;
- owner/household authorization applies to details and aggregates;
- financial mutations define idempotency and correction behavior;
- derived financial responses expose requested/as-of context, source/quality/coverage, calculation version and projection status as applicable.
